# Security audit, 2026-10-30

Scope: the whole repository at the head of `feat/categorization-rules` (API, packages, web, Docker,
CI), with extra attention to what this branch adds: sealed original narrations, owner rules, and
the new routes. Method: reading the code paths named below, targeted searches (raw SQL, logging,
CORS and auth, tracked secrets), `pip-audit` and `npm audit`, and tests for each fix. It is a
review by one reader, not a penetration test; where something was not tested it says so.

## Summary

| # | Finding | Severity | Status |
|---|---|---|---|
| 1 | API accepts any `Host` and cross-site writes (DNS rebinding, cross-site form post) | Medium | Fixed |
| 2 | Failed SQL statements put their bound values (narrations, amounts) in error text and logs | Medium | Fixed |
| 3 | The API has no authentication | Accepted by design, High if ever exposed | Documented |
| 4 | Sealed originals: the key lives on the same host as the database | Low, inherent | Documented |
| 5 | Upload size is capped, but decompressed size of an `.xlsx` is not | Low | Open, untested |
| 6 | Python advisories in `litellm` and `opentelemetry-api` | Low | Accepted in CI, reasons recorded |
| 7 | npm advisory: `systeminformation` (high) via `shadcn` | Low in practice | Open |
| 8 | Narrations are untrusted text inside model prompts | Low | Mitigated by design |

## Findings

### 1. No host or origin checks (fixed)
`api/src/cfo/api/app.py` had no CORS configuration, no `TrustedHost` and no origin check. A page on
any website in the owner's browser could send a form post to `127.0.0.1:8000`, or use DNS
rebinding to make an attacker's domain resolve to it and then read responses. With this branch the
API can return decrypted original narrations, so the impact of that gap grew.
Fix: `api/src/cfo/api/guard.py` refuses a `Host` that is not this machine or the web service, and a
browser `Origin` on any request that changes data that is not one of them. `ALLOWED_HOSTS`
(comma separated) extends the list for a non-default setup. Tests: `api/tests/test_guard.py`.
Not verified against the running Docker stack: the web service proxies with `Host: api:8000` or
`localhost:3000`, and both are allowed, but check the app loads after rebuilding.

### 2. Bound values in database errors (fixed)
SQLAlchemy includes `[parameters: ...]` in the text of a failed statement, and
`errors.py` logs unhandled exceptions with `log.exception`. A failed insert of a transaction would
therefore write its narration into the container log. Fix: `hide_parameters=True` on the engine
(`repositories/db.py`). Test in `test_repositories.py`.

### 3. No authentication (by design, documented)
Every route under `/people/{id}` trusts the id in the path; `GET /people` lists everyone. Isolation
between people is by ledger scope, not by identity. This is acceptable for a single-household app
reachable only from the same machine: `docker-compose.yml` publishes ports on `127.0.0.1` and the
database publishes none. If the API is ever reachable from another machine (a changed port mapping,
a tunnel, a shared host) anyone who can reach it can read and change everything. Do not do that
without adding authentication first.

### 4. Sealed originals (new data, documented)
Original narrations are stored encrypted (Fernet: AES-128-CBC with HMAC-SHA256) in
`posting_originals`. What it protects: a leaked database dump or backup shows ciphertext. What it
does not: someone with the host can read the key (`/keys/narration.key` in a Docker volume, or
`NARRATION_KEY`) and the database. The key file is created with mode 0600. The text is decrypted
only in the API process, for the owner's transaction list and inbox and for local rule matching;
tests assert it is absent from the model-preview endpoint, and the chat tools (five read-only
`get_*` functions) never read it. Removing a statement, ignoring a row or deleting an account
deletes its originals. A lost key degrades to the redacted text without an error. Back the key up
with the database: `make backup` covers only the database.

### 5. Decompressed size of uploads (open)
`read_document` caps the upload at 10 MiB and 20,000 rows, allows four extensions and sniffs the
real type from the bytes. I did not find a limit on how large an `.xlsx` (a zip) expands, and did
not test one. It needs the owner to upload a hostile file to their own app, so it is low.

### 6. Python dependencies
`pip-audit` reports advisories in `litellm` (proxy-server issues; the app uses it as a library)
and `opentelemetry-api` (fix blocked by `google-adk`). `.github/pip-audit-ignore.txt` records the
reasons and CI fails on anything new. I found no change that makes them worse.

### 7. npm dependencies
`npm audit --omit=dev`: four advisories (three low, one high). The high one,
`systeminformation` (Windows command injection), arrives through `shadcn` → `@dotenvx/dotenvx`, a
build-time CLI, not code that serves requests. Update `shadcn` when a release drops it. I did not
inspect the three low ones.

### 8. Untrusted text in prompts
Statement narrations go into model prompts, so a crafted narration could try to instruct the model.
The categorizer accepts only a category key that was offered for that line (`_parse` and the
Decisions path), so the worst outcome is a wrong category, not an action. The chat tools cannot
write. The owner's examples are masked the same way as everything else and carry category keys,
not paths.

## Checked and found fine
- SQL: every query is parameterised; the only f-string SQL is the test fixture's `TRUNCATE`.
- Secrets: `.env` and `statements/` are gitignored and nothing sensitive is tracked.
- Containers: the API runs as a non-root user; PostgreSQL publishes no host port.
- New routes: rule text is capped (200), names (80), reorder lists (500); there are no regex rules,
  so no ReDoS; every route is scoped to the person's ledger; a rule's target must be a live
  category or money in transit.
- CI: CodeQL, dependency review and a scheduled audit are present with read-only permissions.
